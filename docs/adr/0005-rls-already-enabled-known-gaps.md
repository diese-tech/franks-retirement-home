# RLS is disabled on every existing table — this ADR was originally wrong

Status: accepted (correction — see below)

**Correction:** this ADR originally claimed RLS was already enabled across FRH's schema, checked "24 public-read tables" and "8 locked-down sensitive tables," and listed known gaps (an open `registrations` insert policy, a public `match-screenshots` bucket, mutable-search-path functions). None of that was checked against FRH's actual Supabase project — it was checked against an unrelated project (`jsoxhhyveorbplcxqhqo`) that happened to be visible through the same tool connection. That project doesn't back this app; FRH's real project is `vxfakbgrmiqrstigjlug`. The tables and functions cited in the original "known gaps" section (`registrations`, `match-screenshots`) don't even exist in FRH's actual schema.

**The real state**, confirmed directly against `vxfakbgrmiqrstigjlug`: RLS is disabled on all 38 `public` tables, with no exceptions — every one of them is flagged as an `ERROR`-level "RLS Disabled in Public" lint by Supabase's own advisor. This is a real, pre-existing gap, not a documentation-only concern: any table in `public` is reachable through Supabase's always-on PostgREST API unless RLS is enabled, regardless of whether the app itself uses that API.

**What still holds:** `docs/s9-draft-architecture-plan.md`'s "Supabase Realtime and RLS must not enter FRH" is about the app's own authorization logic not depending on RLS/Realtime — FRH's Prisma layer does its own checks in API routes, and the SSE polling pattern uses ordinary `SELECT`s, not `LISTEN/NOTIFY`. That's still true and still fine. Separately, the `postgres` role Prisma connects through has `rolbypassrls = true` on the real project too, confirmed directly — so enabling RLS (with or without policies) on any table would not affect the app's own behavior. It would only close the direct-PostgREST-API surface.

**Scope of this correction:** as of this commit, none of the 38 tables above have RLS enabled — that's the count including only what's actually merged to `main`. The tournament bracket feature's `Tournament`/`Participant`/`BracketMatch` tables are still in flight in a separate PR; that migration enables RLS with no policies on those three (the same safe default-deny posture described above), but until it merges, this document should not be read as describing current state for them. Enabling RLS on the pre-existing 38 tables is a larger, separate piece of work — outside the bracket feature's scope — and is not done as part of this correction.

## Final correction (2026-07-26): gap closed, RLS now enabled project-wide

`prisma/migrations/20260725120000_enable_rls_legacy_tables/migration.sql` (Workstream 3 of `docs/production-readiness-implementation-plan.md`) closes the gap described above: it enables RLS, with **no policies**, on every remaining `public` table that didn't already have it. Once that migration merges and deploys, RLS (default-deny for `anon`/`authenticated`, no exceptions) is enabled on **every table in `public`**, matching the same pattern already used for `Tournament`/`Participant`/`BracketMatch` in `prisma/migrations/20260724230000_tournament_bracket/migration.sql`. As established above, this has zero effect on the app's own behavior — Prisma connects through the `postgres` role, which has `rolbypassrls = true`, confirmed directly against `vxfakbgrmiqrstigjlug` — so this only closes the direct-PostgREST-API surface.

One correction to the count itself: querying the live project directly (`list_tables` + `get_advisors` against `vxfakbgrmiqrstigjlug`, not hand-copied from this document) turned up **40** pre-existing tables still flagged by the `RLS Disabled in Public` advisor lint, not 38. The difference is two tables this document's earlier count missed: `_prisma_migrations` (Prisma's own internal migration-bookkeeping table — it lives in `public` and is exposed to PostgREST exactly like any app table, so it's included in the new migration too) and one additional application table (`ChangeRequest`, added by `prisma/migrations/20260529172000_add_change_requests`, predates this ADR's prior correction but wasn't included in its tally). Cross-checked against `prisma/schema.prisma`: 42 models total, minus the 3 tournament-bracket tables that already had RLS = 39 pre-existing app tables, plus the 1 system table (`_prisma_migrations`) = 40, matching the advisor's live count exactly.

With this migration merged and deployed, there are no more open items tracked by this ADR: the `rls_disabled_in_public` ERROR-level finding is fully resolved project-wide, with zero policies added and zero effect on application behavior.
