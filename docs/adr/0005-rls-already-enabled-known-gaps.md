# RLS is disabled on every existing table — this ADR was originally wrong

Status: accepted (correction — see below)

**Correction:** this ADR originally claimed RLS was already enabled across FRH's schema, checked "24 public-read tables" and "8 locked-down sensitive tables," and listed known gaps (an open `registrations` insert policy, a public `match-screenshots` bucket, mutable-search-path functions). None of that was checked against FRH's actual Supabase project — it was checked against an unrelated project (`jsoxhhyveorbplcxqhqo`) that happened to be visible through the same tool connection. That project doesn't back this app; FRH's real project is `vxfakbgrmiqrstigjlug`. The tables and functions cited in the original "known gaps" section (`registrations`, `match-screenshots`) don't even exist in FRH's actual schema.

**The real state**, confirmed directly against `vxfakbgrmiqrstigjlug`: RLS is disabled on all 38 `public` tables, with no exceptions — every one of them is flagged as an `ERROR`-level "RLS Disabled in Public" lint by Supabase's own advisor. This is a real, pre-existing gap, not a documentation-only concern: any table in `public` is reachable through Supabase's always-on PostgREST API unless RLS is enabled, regardless of whether the app itself uses that API.

**What still holds:** `docs/s9-draft-architecture-plan.md`'s "Supabase Realtime and RLS must not enter FRH" is about the app's own authorization logic not depending on RLS/Realtime — FRH's Prisma layer does its own checks in API routes, and the SSE polling pattern uses ordinary `SELECT`s, not `LISTEN/NOTIFY`. That's still true and still fine. Separately, the `postgres` role Prisma connects through has `rolbypassrls = true` on the real project too, confirmed directly — so enabling RLS (with or without policies) on any table would not affect the app's own behavior. It would only close the direct-PostgREST-API surface.

**Scope of this correction:** the three new tables added for the tournament bracket feature (`Tournament`, `Participant`, `BracketMatch`) do have RLS enabled with no policies, matching the safe default-deny posture described above (see the feature's own migration). Enabling RLS on the other 35 pre-existing tables is a larger, separate piece of work — outside this feature's scope — and is not done as part of this correction.
